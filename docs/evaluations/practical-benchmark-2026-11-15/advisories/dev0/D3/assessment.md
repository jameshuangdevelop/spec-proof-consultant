### O1 — Iterate malformed-record and partial-callback contract

- Priority: first. Malformed records can produce callback effects before an error; negative tests should capture the intended boundary. Source/test work appears small; verifier feasibility is unknown.
- Target/boundary: r1:db/write_batch.cc:42 `WriteBatch::Iterate` indexes Slice input and invokes GetLengthPrefixedSlice, Handler::Put/Delete and Count. :134 `WriteBatchInternal::InsertInto` obtains Sequence before Iterate; :118 `MemTableInserter` writes to MemTable and increments sequence. Handler is a virtual interface (r1:include/leveldb/write_batch.h:33–38). Slice/coding/Status/memtable/dbformat bodies are unread; full semantic closure absent. r1:db/db_impl.cc:1236–1245 logs then inserts while mutex temporarily unlocked under writer serialization; this caller observation is not a durability, rollback or race-freedom proof.
- Requirement: byte layout **documented** at r1:db/write_batch.cc:5–14; ordered updates **documented** in public header :7–14. Error classification and valid-prefix callback effects **inferred** from Iterate; r1:db/write_batch_test.cc:75–86 records a prefix plus ParseError example. Owner authority, arbitrary corrupt-input admission and callback mutation/throwing behavior **unresolved**. SetContents asserts at least kHeader (:139–142), and InsertInto reads Sequence before Iterate, so Iterate's short-input check does not establish safety of all callers with short internal representations.
- Property: candidate domain for Iterate is any finite representation byte string, including length <12, invalid tags, truncated/overlong length encodings, count mismatch and empty records, with a valid nonmutating recording Handler and stable representation during the call. Normal-return contract candidate: <12 returns Corruption with no callbacks; each fully decoded record generates exactly one ordered matching callback; invalid/truncated records return Corruption after the valid prefix only; count mismatch is checked after decoded callbacks, and OK requires complete parsing plus matching count. Whether this becomes approved intent remains unresolved; callback exceptions/mutation require separate contract decisions, not an assumption of safety. Loop invariant candidate: consumed input corresponds to the header plus decoded record prefix; callbacks match that prefix; found equals attempted records, including the current failed attempt; each successful iteration consumes at least the tag. Counterexamples: invalid access, callback on an incompletely decoded record, OK with wrong count, or prefix effects inconsistent with the approved contract. `found` is signed int (:50–52); extreme record counts and integer conversion/overflow are unresolved real-domain limits, not silently excluded from the product contract. No rollback assertion is justified.
- Method: first noncatalog source inspection and proposed native negative tests. `cbmc-c-buffer` **1.0.0**, bundled `references/cbmc.md`, is only an investigation lead from indexing, **compatibility unknown**. Conditional assurance exactly: “Enabled memory/UB checks and assertions over the modeled C/C++ harness domain with complete unwinding and specified platform model.” Requires actual callee bodies, C++ features/virtual dispatch/string/allocation support, flags/includes, architecture and approved buffer/loop bounds. Hard exclusions assembly, concurrency and FFI cannot be overridden; the DB caller is not a supported sequential parser harness. C++ linkage alone is not evidence of FFI. Does not cover unbounded loops/heap or unread external bodies. Do not use success stubs to claim native implementation verification.
- Alternatives: native recording-handler tests isolate callback observations better than the existing memtable printer but are non-proof. Defer TLC: an abstract parser model would not verify C++ byte decoding. Defer full CBMC until closure/support/domain are established, without weakening malformed-input expectations.
- Readiness: evidence gathering precedes owner intent and method selection. No tool release support, test pass or implementation/execution approval established.

- Priority: second; modest incremental contract coverage over existing empty/nonempty append examples, with arithmetic and alias uncertainty.

- Requirement: copying source operations **documented** at r1:include/leveldb/write_batch.h:65–70. Self-append, invalid headers, signed-count overflow, oversized records and allocation-failure behavior **unresolved**, without owner approval. Public source reference can alias this; do not exclude it just because inspected caller examples use distinct objects.
- Property: for valid encoded batches, on normal return destination operation sequence should equal old destination followed by old source; source should remain unchanged when distinct, destination sequence should remain its old sequence, and header count should equal decoded records. Empty source/destination, duplicate keys, deletion records, aliasing and count-width boundaries need explicit oracles. Candidate intended self-append would duplicate old operations, but is not yet approved and must be analyzed with std::string alias semantics. Arithmetic representability must be decided, not assumed away to gain a pass. No loop invariant in the wrapper; coding/string internals remain unknown. Counterexamples: altered source, lost/duplicated payload, unexpected destination sequence or count disagreement/UB.
- Method: noncatalog source contract investigation plus conditional native tests; no verifier assurance claimed. CBMC bitvector guide does not automatically support string append or integer policy: required data model, bodies and overflow intent absent. Compatibility unknown.
- Alternatives/readiness: reject storage-wide atomicity/durability claims from this wrapper. Defer proof/repair until encoding, alias/overflow/exception intent, dependency closure and actual owner grants are resolved. A newly found mismatch should be handed back, not repaired in this assignment.
