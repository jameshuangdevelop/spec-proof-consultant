### O1 — Clarify and check terminal write-state behavior

- **Priority and rationale:** P1 planning lead. A connection used after an I/O error or sent close must not resume network writes. Existing selected tests sample deadline acceptance and pool cleanup, but do not establish first-error retention and subsequent no-I/O behavior. A counter-instrumented fake connection looks cheaper than an abstract model; actual effort remains unknown.
- **Target and boundary:** `r1:conn.go:359` Conn.writeFatal stores an error only if writeErr is nil, under writeErrMu, but returns the current argument, not necessarily the stored error. `r1:conn.go:379` Conn.write serializes with mu, checks writeErr before SetWriteDeadline/Write or writeBufs, and records ErrCloseSent after successful CloseMessage. `r1:conn.go:415` WriteControl validates before acquiring mu; expired deadline/wait timeout returns without writeFatal; after acquisition, `r1:conn.go:462` applies the same error gate. `r1:conn.go:189` newMaskKey depends on crypto/rand and `maskBytes` is uninspected, so client encoding correctness is not claimed. `r1:conn.go:407` writeBufs calls Go net.Buffers.WriteTo, whose implementation is unread.
- **Caller/configuration closure:** newConn seeds mu with one token (`r1:conn.go:305`); client and server instantiate it at `r1:client.go:326` and `r1:server.go:213`. Server compression hooks are installed at `r1:server.go:216`; their bodies are excluded. messageWriter.flushFrame calls write at `r1:conn.go:630`; Close calls flushFrame at `r1:conn.go:740`; WriteMessage has a server uncompressed fast path at `r1:conn.go:769`. PreparedMessage.frame at `r1:conn.go:745` is unread. `r1:go.mod:3` declares Go 1.20, not a reproduced toolchain. `r1:doc.go:126` requires one ordinary writer, and `r1:doc.go:133` permits concurrent Close and WriteControl. Best-effort isWriting panic detection is not race freedom.
- **Requirement:** **documented**: a timed-out write corrupts the websocket state and future writes return an error (`r1:conn.go:792`, SetWriteDeadline documentation). **Inferred**: once a nonnil writeErr is stored, later valid operations that reach the write-error gate return that stored error without further connection I/O. **Unresolved**: whether the documented timeout promise includes expiration before acquiring mu; exact error identity across all public APIs; treatment of interrupted in-flight operations and previous-writer Close failures. Owner authority and approval have not been obtained. Existing assertions do not decide these questions.
- **Property/domain:** candidate traces start from a properly initialized Conn with one ordinary writer and, optionally, concurrent control operations. Include successful/failing SetWriteDeadline and Write, successful CloseMessage, zero/future/expired deadlines, control payload lengths 0, 125 and invalid 126, and invalid opcodes. At completed error-gate transitions, invariant: writeErr changes only from nil to a first nonnil error and never back; acquired mu is returned on normal error/success exits. After storing a fatal error, a later valid gate-reaching operation must return it and not increment connection deadline/write counters. A successful close returns success for that operation but leaves later valid writes blocked by ErrCloseSent. Validation/pre-lock timeout may return their own error and must be tracked separately, not assumed permanently fatal. Counterexamples: overwritten/cleared sticky error, subsequent network call, lost mutex token, or sticky poisoning by a pre-acquisition timeout if the approved contract excludes it. No scheduler progress or panic recovery property is promised.

It has no catalog hard exclusion, but tool/Java versions, abstraction and source correspondence are unresolved.
