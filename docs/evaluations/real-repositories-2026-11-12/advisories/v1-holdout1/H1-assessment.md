## Decisions

One opportunity is justified: make the lexical/configuration contract explicit and investigate a nonduplicative bounded contract matrix. Do **not** replace this mature parser or add another suite of the already-present mixed-case/high-byte/long-exponent examples. No defect or missing-test claim is established by this sample.

### O1 — P1: clarify constructor domain, then exercise count/rejection interactions

**Value and cost.** Parsed-length and rejection semantics matter to downstream parsers even when the numerical value is correct. The implementation has many flag interactions; current inspected tests provide strong individual regressions but do not by themselves establish a complete flag × explicit-length × code-unit contract matrix. Incremental value is the interaction inventory and missing-case decision, not more copies of existing cases. Read-only contract mapping is small; test/harness cost and duplication remain unknown until the inventory is completed.

**Target/boundary.** `StringToDoubleConverter` constructor and public byte/uc16 double/float APIs, through `StringToIeee`, `Advance`, whitespace and symbol helpers (citations above). Numerical conversion and standard-library locale/math bodies are still reached for the full input domain. There is no observed async/concurrency or foreign-language implementation in these inspected paths; C++ linkage is not FFI. Locale internals, `ldexp`, floating environment, assertion macros, target integer/char data model and uninspected decimal dependencies prevent claiming tool compatibility.

**Requirement classification and authority.**

- **Documented:** separators only between significand digits, not exponent/leading/trailing/repeated; malformed non-number input is junk; processed spaces count and trailing junk does not (`string-to-double.h:58-117,195-201`). Flags decide whether the suffix is rejected or ignored, so a universal “invalid separator always rejects” property would be wrong.
- **Inferred from source, not approved intent:** junk exits preserve count zero; caller supplies nonnegative length within one live array, a writable count pointer, stable readable configured symbol strings; even length zero uses pointer arithmetic. Null-buffer-with-zero-length, negative lengths, overlapping output/input storage and invalid lifetimes have no established rejection contract.
- **Unresolved:** are non-null **empty** symbol strings permitted? The documented first-character restrictions (`string-to-double.h:95-108`) do not explicitly settle that case. `ConsumeFirstCharacter` reads `str[0]`; `ConsumeSubStringImpl` assumes an already-matched first character and advances the symbol pointer (`string-to-double.cc:77-119`). An explicit input code unit NUL and an empty symbol is therefore a source-backed boundary question, not a confirmed valid-input bug or executed reproduction. Similarly, do distinct initial symbol bytes that coincide after case folding violate the “not same first character” rule when case-insensitivity is enabled? Which configured symbol has precedence then? Do not silently exclude these configurations as “invalid” to get a pass.
- The campaign owner authorizes read-only advice only. Upstream/component-owner authority for resolving these obligations and implementing any tests is absent.

**Proposed property/domain.** First retain a full-domain contract table for the documented flag bits (0..255), both character widths and both precisions, custom separator/symbol configurations, empty buffers, embedded NUL, incomplete exponent/sign, and extreme representable lengths. Resolve the constructor ambiguities above. A subsequent **finite native-test pilot**, if approved, can use valid distinct live storage of length 0..32, byte and uc16 arrays (not C-string truncation), all documented flag combinations, no separator / apostrophe / space / U+202F, disabled symbols and `"Infinity"`/`"NaN"` under both case modes. These are proposed bounds, not limitations of the API. Empty/case-colliding symbol configurations stay explicit pending owner decision, not assumptions that disappear.

For each approved configuration, expected output is the configured empty/junk sentinel or the parsed value/category, with count exactly the accepted prefix including allowed spaces and excluding junk; rejection count-zero is a separately approved inferred contract. Compare signed-zero bits and NaN category rather than ordinary equality. Use lexical cases with exact small integer results and special values to avoid treating host `strtod` or double-to-float casting as an oracle. Byte/uc16 equivalence applies to the shared ASCII domain only: high byte 0xA0 and uc16 U+00A0 intentionally differ. Invariants to investigate: every dereference is within `[input,end)`, iterator remains between the endpoints, count is in `[0,length]`, separator lookahead stays in range, collected decimal digits fit `kBufferSize`, and no cursor dereference follows `parsing_done` (`string-to-double.cc:582-591,733-746,864-924`). Counterexamples are an out-of-range access, an incorrect count/category/value for an approved table row, inappropriate wide/byte alias matching, or silent acceptance/rejection inconsistent with flag policy. Examples to retain include `"0x"` under trailing-junk, `"123e-"` with and without trailing-junk, `"1.0e1 000"` with space separator, truncated `"Infinity"` at each explicit length, and embedded NUL. These are proposed checks, not observed failures.

**Method and alternatives.** Prefer noncatalog source contract review followed, only if gaps remain, by native table/property tests: observed executions, not proof. Curated `cbmc-c-buffer` **1.0.0**, `references/cbmc.md`, matches indexing/pointer goals, but is a conditional investigation, **compatibility unknown and implementation blocked**. Its assurance is “Enabled memory/UB checks and assertions over the modeled C/C++ harness domain with complete unwinding and specified platform model.” It hard-excludes assembly, concurrency and FFI. Before any pilot, inspect every reached callee/configuration, pin compilation/data model and resolve locale/math/C++ support, allocation/stubs, loop bounds and enabled checks. Do not stub the numerical conversion or `ToLower` as successful and call that verification of the original parser. A special-symbol-only lexical subdomain might avoid some numerical calls but would prove nothing about remaining inputs and still reaches locale for case folding. Small bounds do not test the 772-digit buffer limit or INT_MAX exponent/length arguments; retain those larger obligations explicitly. `cbmc-c-bitvector` in the same guide is not a substitute for floating rounding correctness.

Reject replacement/code-generation: no opt-in and high equivalence/integration cost. Defer whole numerical proof or a new rounding-oracle suite: existing precise regressions and uninspected arithmetic/math boundaries make incremental benefit/cost uncertain. Existing fuzzing is an alternative bug-finding route after authorization, not exhaustive assurance.
