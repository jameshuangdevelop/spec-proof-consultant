### O1 — P1: span independence and ASCII width agreement

- **Impact/cost:** protects downstream parsers using substrings, embedded NUL or adjacent unconsumed storage. Small test-only scope after inventory; likely cheaper than a solver port. Incremental coverage is a hypothesis, not a claim that the entire corpus lacks these tests.
- **Requirement/authority:** explicit length and “same ... for 16 bit characters” are documented (`r1:double-conversion/string-to-double.h:183-203`). Independence from storage outside the span and exact ASCII widening agreement are inferred consequences to confirm with upstream/component owner. Count-on-rejection being zero is observed in implementation/tests, but the general failure-count policy is not explicitly documented there; resolve before promising it as public intent. No upstream or implementation approval exists.
- **Proposition/domain:** two calls of the same overload with identical converter configuration and identical first `n` code units, but arbitrary different suffixes outside the selected span, produce equivalent value classifications/bits and identical counts. Compare float only with float and double only with double. Also, for code units `0..127`, widening each byte to uc16 with the same ASCII separator/symbols produces identical values and counts. Use fixed `empty=2`, `junk=3`, null or nonempty valid distinct-first-character special symbols such as `"Infinity"`/`"NaN"`; flags drawn from the eight documented bits. Preserve signed zero; compare NaNs by classification rather than payload. Do not generalize width equivalence to `0x80..0xff`: U+00A0 is deliberately whitespace only in the uc16 path.
- **Preconditions:** `0 <= n <= INT_MAX`; input points to a live, readable array supporting pointer arithmetic through `n`, even at zero length; count points to distinct writable `int`; symbol strings remain live, terminated and obey documented restrictions. No requirement to terminate the input at `n`. Do not infer defined behavior for negative lengths or null pointers from this proposal. For practical native cases start at `n=0..8` and selected longer prefixes; these bounds do not discharge larger-span obligations.
- **Postconditions/invariants:** `0 <= count <= n`; outside-span changes must not affect the result. Inspect the intended iterator invariant `input <= current <= end` and dereference only when `current != end` (`r1:double-conversion/string-to-double.cc:582-590`); emitted decimal buffer length stays within `kMaxSignificantDigits` plus the sticky digit and terminator (`:727-791`, `:903-908`). Runtime examples do not prove these invariants.
- **Concrete negative/boundary cases for owner review:** raw arrays `{'1','e','+','9'}` with lengths 1, 2, 3 versus 4; with trailing junk allowed the incomplete exponent prefixes consume only the numeric prefix, not `e+`. `{'1',0,'2'}` at length 3 must not acquire C-string semantics: expected junk/count policy must be approved; source suggests rejection without trailing junk and prefix consumption with it. Include zero-length nonnull arrays, lone sign, `"0x"`, separator before/after decimal point, separator in exponent, and allowed trailing spaces followed by junk. These are unexecuted proposed cases, not discovered failures.
- **Counterexample:** suffix mutation changing value/count; count outside `[0,n]`; disagreement between ASCII and widened ASCII on the same overload; or a rejected/partial token consuming junk contrary to the approved table. Width agreement alone can miss common-mode parser bugs, so independently expected count/error rows remain necessary.
- **Method:** explicit noncatalog native property/regression tests plus source contract review, not proof. Test-only additions to `test/cctest/test-conversions.cc`, if separately authorized, must call the actual converter with explicit lengths rather than the strlen helper. Preserve existing production and existing failures. Sample execution would establish only tested behavior.
- **Boundary/configuration:** special matching can reach `std::locale::classic`/`std::ctype::tolower` (`r1:double-conversion/string-to-double.cc:57-123`); hex conversion reaches `ldexp`; decimal paths reach the unread dependency closure above. Signed-char behavior and floating models require recorded compiler configuration; architecture selection is explicit in `r1:double-conversion/utils.h:138-165`. No actual FFI, assembly or concurrent caller was established; missing library bodies are unknowns, not proof of FFI.
- **Alternatives:** CBMC `cbmc-c-buffer` v1.0.0, bundled `references/cbmc.md`, fits pointer/index concerns only conditionally: enabled memory/UB checks and assertions over the modeled C/C++ harness domain with complete unwinding and specified platform model. It excludes assembly/concurrency/FFI and requires flags, bodies, allocation/loop bounds and supported C++ features. Exact release compatibility, locale/math modeling and decimal closure are unknown, so a native parser pilot is blocked. Do not stub successful conversion to claim parser correctness. A helper-only `Advance` experiment would cover only helper behavior, not these API properties. Fuzz/sanitizer work could find sampled errors after approval, not prove absence. Numerical rounding proof is deferred: it needs exact floating/rounding requirements and the larger callee boundary; existing rounding tests make duplicative examples low priority. Replacement/codegen has no adoption grant.
