### Actual source and assurance boundary

- SmallRng selects xoshiro128++ on 16/32-bit pointer targets and xoshiro256++ on 64-bit targets (`r1:src/rngs/small.rs:14-17`). Both named algorithms are separately exported, independent of pointer width (`r1:src/rngs/mod.rs:97-109`). A host test of the named 128-bit algorithm is not a test of SmallRng's 32-bit alias.
- SmallRng explicitly disclaims cryptographic security and portability across versions/platforms (`r1:src/rngs/small.rs:19-41`); the named algorithms have a separate documented reproducibility category (`r1:src/rngs/mod.rs:41-49`). Do not promote the SmallRng golden sequences to cross-platform/cross-version public requirements.
- Public SmallRng Seed is always 32 bytes, but `from_seed` slices to the selected algorithm seed size before delegation (`r1:src/rngs/small.rs:81-96`). That size is 16 bytes for Xoshiro128PlusPlus and 32 for Xoshiro256PlusPlus (`r1:src/rngs/xoshiro128plusplus.rs:28-41`; `r1:src/rngs/xoshiro256plusplus.rs:28-41`). Thus last-half seed changes have no effect on 16/32-bit SmallRng in this revision. It is not a seed-injective interface.
- Both from_seed methods call external `rand_core::utils::read_words`, check the resulting words for all zero, then call seed_from_u64(0) if zero. The seed_from_u64 bodies use local wrapping SplitMix64 arithmetic with two versus four iterations (`r1:src/rngs/xoshiro128plusplus.rs:44-64`; `r1:src/rngs/xoshiro256plusplus.rs:44-63`). Comments/debug assertions state a nonzero result, not a proof over all u64 seeds.
- Native-word steps use explicit wrapping adds, fixed shifts and rotations. The 128-bit algorithm's native word is u32 (`r1:src/rngs/xoshiro128plusplus.rs:67-89`); u64 requests delegate to `utils::next_u64_via_u32` (`:91-94`). The 256-bit algorithm emits u64; u32 takes its high 32 bits and advances once (`r1:src/rngs/xoshiro256plusplus.rs:66-95`). Both fill_bytes delegate to external `utils::fill_bytes_via_next_word`, using different native widths (`:97-100` and `r1:src/rngs/xoshiro128plusplus.rs:96-99`). SmallRng just forwards all three TryRng methods (`r1:src/rngs/small.rs:100-116`).
- Cargo specifies `rand_core = "0.10.0"` with default features false, not an exact resolved dependency commit (`r1:Cargo.toml:63-68`); Rust minimum 1.85 and edition 2024 are declared (`:15-16`). The external helpers, blanket Rng trait behavior and seed-byte ordering are **not established** by their names. Trait/helper bodies are not in the selected source scope. No fetch, dependency-cache search or vendored copy was used. Missing bodies are not evidence of FFI or dynamic dispatch.
- Optional serde derives are present only on named generators (`r1:src/rngs/xoshiro128plusplus.rs:11-24`; same lines in xoshiro256plusplus). SmallRng has no such derive in its inspected file. Deserialization may introduce states not reached by normal constructors; preserve arbitrary-state obligations for step properties rather than assume constructor-only states universally.
- `r1:src/lib.rs:36-65` is no_std, conditionally enables feature-specific code and re-exports rand_core traits. The selected primitive steps show no unsafe, FFI, async, assembly or dynamic dispatch; this is a bounded observation, not proof about external helpers or the whole default-feature crate.

Embedded `reference` tests contain ten expected native words attributed by comments to the reference algorithms (`r1:src/rngs/xoshiro128plusplus.rs:107-122`; `r1:src/rngs/xoshiro256plusplus.rs:108-131`). `stable_seed_from_u64_and_from_seed` compares zero seeds against ten values (`:125-140` / `:134-157`) while explicitly disclaiming SmallRng stability. These are sample known-answer artifacts, not reproduced results or independently checked upstream reference provenance. CI defines x86_64/i686, feature combinations, powerpc cross tests and Miri (`r1:.github/workflows/test.yml:60-177`); no actual outcomes were inspected. ## Decisions

Two opportunities. First resolve the public architecture/helper contract; second consider a very small native arithmetic check. Do not start whole-RNG proofs, randomness statistics, period/security claims, or algorithm replacement. Costs below are relative scope estimates, not measured runtimes.

### O1 — P1: current-revision seed projection and mixed-call consumption

- **Value/effort:** small documentation/test inventory, potentially moderate dependency inspection. It can prevent downstream reproducibility bugs from assuming all 32 seed bytes or a concatenated byte stream behave identically everywhere. Existing native-word vectors do not settle this API boundary.
- **Requirements/authority:** fixed Seed size is documented in code (`r1:src/rngs/small.rs:82-83`); projection and delegation are observed implementation behavior (`:86-116`). Promise of exact mixed-call consumption, tail buffering, byte ordering and whether to document ignored seed bytes is unresolved pending upstream/component-owner input and dependency evidence. Campaign owner cannot resolve it. No actual implementation/test approval.
- **Property A/domain:** all `[u8;32]` seeds, no precondition excluding zero. On 16/32-bit selected configuration, SmallRng::from_seed(a) equals its selected Xoshiro128PlusPlus constructed from `a[..16]`; seeds sharing the first 16 bytes yield identical initial state and subsequent same-method observations. On 64-bit, delegate all 32 bytes to Xoshiro256PlusPlus. Assert slice conversion never panics in these configurations (LEN=16 or 32); other pointer widths have no selected alias and are not an established supported build. No claim that differing prefixes must yield differing streams.
- **Property B/domain:** any valid constructed state, cloned before comparison; arbitrary legal destination slice lengths. Establish expected word consumption and byte order by reading exact resolved rand_core bodies before specifying fill assertions. An initial finite native-test proposal covers lengths 0..17 (around both 4- and 8-byte boundaries), canary subslices and sequences mixing next_u32, next_u64 and fill_bytes. Preconditions: exclusive mutable access to each RNG and destination; no concurrency. No error is expected from the selected Infallible methods, but that type alone does not prove panic freedom, byte semantics or advancement.
- **Postconditions/invariants:** wrapper calls yield the same outputs, destination bytes and next state as direct selected-method delegation. For accepted byte semantics, bytes outside the chosen destination stay unchanged and advancement equals the helper's actual consumption rule. Track state after every call, not just output. Loop invariant for external fill cannot yet be stated source-groundedly: W1 must record written-prefix/consumed-word/partial-tail behavior; implementation remains blocked meanwhile.
- **Counterexamples and negative review:** on 32-bit, two seeds with first 16 bytes zero and a differing last byte must not be assumed distinct—both take the all-zero prefix fallback. Test 64-bit forwarding without assuming seed injectivity. A plausible but unapproved law `fill(a);fill(b) == fill(a||b)` may fail when a call discards an unused word tail; never adopt it without the helper body. Zero-length fills may or may not advance without that evidence. These are explicit unresolved contract challenges, not claimed failures. No general cross-architecture equality is expected.
- **Boundary/method:** noncatalog source contract review and proposed architecture-specific native regression, not proof. Need exact rand_core source identity and `read_words`, `next_u64_via_u32`, `fill_bytes_via_next_word`, SeedableRng/TryRng/Rng adapter bodies. Request separately supplied read-only dependency scope; do not broaden the present target selection or assume little-endian semantics solely from reference vectors.
- **Alternatives:** defer a `kani-rust-slices` v1.0.0 full-fill pilot (bundled Kani guide): assurance would be enabled checks/assertions over the stated finite harness domain with complete unwinding, not larger slices or excluded dependencies. Helper bodies, loops, toolchain/feature compatibility and intended bytes are unknown; a successful stub would not verify real helpers. Native direct-delegation tests avoid a port but can share a helper bug; independent expected byte rows become necessary after W1. No need for source replacement.

### O2 — P2: nonzero-state and one-step arithmetic integrity on existing kernels

- **Value/cost:** finite fixed-width kernel is more tractable than seeding/fill integration; can cover arbitrary states beyond ten reference vectors. Solver multiplication in SplitMix may be costly; feasibility/time is unknown. Approve property before adding a harness.
- **Requirement:** from_seed documents all-zero remapping (`r1:src/rngs/xoshiro128plusplus.rs:31-39`; same for 256); nonzero seed_from_u64 is stated in comments/debug assertions (`:60-62` / `:59-61`). Preserving nonzero state under a native step and exact current-algorithm equations are inferred algorithm-integrity propositions. Owner confirmation missing; no requirement that every emitted word be nonzero or statistically independent.
- **Domain/preconditions:** arbitrary four words of width w=32 or 64 for each named algorithm, including all-zero state in the arithmetic relation. Nonzero preservation is conditional on the old state being nonzero; do not constrain every word nonzero. Separate seed_from_u64 proposition quantifies **all** u64 inputs including zero and overflow-neighbor inputs; it must not assume its output nonzero to prove that fact. SmallRng projection/read_words are outside this isolated step claim.
- **Postconditions:** native step returns Ok and `rotl_w(a+d,r)+a mod 2^w`, with r=7/23. With old words `(a,b,c,d)`, set `C=c xor a`, `D=d xor b`, then next state is `(a xor D, b xor C, C xor (b << k mod 2^w), rotl_w(D,q))`, k=9/17, q=11/45. Nonzero input must not map to all zero. Seed_from_u64 must produce a nonzero four-word array for every u64 input under the specified wrapping operations. 256's try_next_u32 must equal the high half of one native u64 result with exactly that next state (`r1:src/rngs/xoshiro256plusplus.rs:70-74`).
- **Invariants/counterexamples:** fixed array length and fixed valid shifts; pure one-step transition has no loop. Seed expansion iterates two chunks or four words; record invariant “i completed native seed chunks correspond to i SplitMix outputs with state advanced by i*PHI modulo 2^64,” initialized at i=0. Counterexamples are a panic/incorrect checked-overflow interpretation, altered transition/output, nonzero-to-zero transition, seed_from_u64 producing zero, or u32 delegation advancing twice/taking the low half. All-zero state can remain zero and output zero; a zero output from nonzero state alone is not a failure. No period, distribution quality or cryptographic property follows.
- **Method fit:** `kani-rust-arithmetic` v1.0.0, bundled `references/kani.md`. Conditional assurance: “Checks enabled safety properties and assertions for all inputs represented by a harness, subject to complete unwinding, models, assumptions, and tool soundness.” Hard exclusions are FFI, concurrency, async, assembly and dynamic dispatch. Selected step bodies appear sequential and fixed-size, but actual monomorphization/core intrinsics, release and crate feature support remain unknown. A local harness must call existing production methods with test/module access to private state, not verify a copied reimplementation alone. The mathematical relation can be independent harness assertions; it is not itself a proof of intended algorithm.
- **Dependencies:** pin compatible Kani/Rust, review rotate/wrapping/slice-iterator support and compiled call graph. Isolating these existing methods is proposed, not demonstrated; unread trait dependencies still block a supported-native pilot claim. Seed_from_u64 is a separate harness from step/from_seed; do not claim constructor coverage from arbitrary-state transition checking.
- **Alternatives:** native edge/known-answer tests can sample max-word, sparse-state and zero-seed behavior with less setup. Existing vectors already serve a useful baseline. An algebraic inverse argument could justify nonzero preservation but is an unexecuted proof proposal, distinct from solver checks. Verus adaptation/whole-RNG proof is not justified by this small contract; no adaptation or replacement grant.
